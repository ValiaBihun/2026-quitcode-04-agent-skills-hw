# Колбек n8n → Next.js

**Ендпоінт.** `POST /api/n8n/<event>` — Route Handler `app/api/n8n/[event]/route.ts`. Route Handler
— публічний HTTP-ендпоінт, тож довіряємо лише підпису.

## Що надсилає n8n

| Заголовок | Значення |
|---|---|
| `content-type` | `application/json` |
| `x-n8n-timestamp` | Unix-час у секундах, коли n8n підписав запит |
| `x-n8n-signature` | `sha256=<hex HMAC-SHA256(N8N_CALLBACK_SECRET, "${timestamp}.${rawBody}")>` |
| `idempotency-key` | `<data.jobId>:<event>` — ті самі значення, що в підписаному тілі |
| `x-correlation-id` | Скопійований із запиту, що запустив воркфлоу |

```json
{
  "version": 1,
  "event": "quote-request.completed",
  "data": {
    "jobId": "5f0c…",
    "status": "completed",
    "correlationId": "9b1e…",
    "requestIdempotencyKey": "c3d4…",
    "result": { "documentUrl": "https://files.example.test/n8n/5f0c….pdf" },
    "completedAt": "2026-09-21T12:00:00.000Z"
  }
}
```

- `data.status` — `completed` або `failed` (тоді замість `result` — `error: { code }`).
- `data.requestIdempotencyKey` — наш `idempotency-key` із запиту, що запустив воркфлоу: за ним
  знаходимо запис (він відомий ще до того, як прийде `job_id`).
- Мок скіла надсилає лише `completed`; подія в тілі — `<path>.completed`.

## Порядок обробки — саме такий

| # | Крок | Відповідь |
|---|---|---|
| 1 | Подія зі шляху невідома; `content-type` не `application/json` — **до** читання тіла | 404; 415 |
| 2 | Прочитати **сирі байти** тіла, один раз, **з обмеженням 64 КБ**: `request.body.getReader()` і зупинитись, щойно сума перевищить ліміт (шаблон `readRawBody`). `request.text()` спершу буферизує все тіло — у Route Handler Next.js ліміту немає. Ні `request.json()`, ні `JSON.parse` до підпису: повторна серіалізація змінює байти | — |
| 3 | Тіло > 64 КБ (читання зупинено на кроці 2) | 413 |
| 4 | `x-n8n-timestamp` не число або відрізняється від поточного часу > 300 с (у будь-який бік) | 401 |
| 5 | HMAC-SHA256 від `` `${timestamp}.${raw}` ``, порівняти з підписом: спершу довжини, потім `crypto.timingSafeEqual` (кидає помилку на різних довжинах). Не `===`. Без подробиць у тілі | 401 |
| 6 | «Застовпити» `idempotency-key` (унікальний запис). Уже був | 200 `{"duplicate":true}` |
| 7 | `JSON.parse(raw)`, перевірка форми: `version`, `event` у тілі — `<path>.…`, `data.jobId`, `data.status`, **`data.requestIdempotencyKey`** (за ним шукаємо запис — без нього тіло некоректне, це 400, а не 500); `idempotency-key` === `` `${data.jobId}:${event}` `` з тіла | 400 (і звільнити ключ) |
| 8 | Зберегти мінімальний стан (`status: "ready"`, посилання) **до** відповіді; збій — звільнити ключ | 500 |
| 9 | Відповісти | 202 `{"ok":true}` |
| 10 | Повільне (листи, сповіщення) — в `after()` | — |

**Чому запис до відповіді.** Отримавши 2xx, n8n колбек не повторить. Якби критичний запис жив лише
в `after()` і впав, результат загубився б назавжди.

**Чому звільняти ключ.** Якщо після кроку 6 обробка впала, а ключ лишився, повтор n8n (Retry On
Fail) отримає `{"duplicate":true}`, і результат загубиться.

**Чому ключ звіряємо з тілом.** Заголовок `idempotency-key` підписом не захищений (HMAC — лише від
`` `${timestamp}.${raw}` ``). Хто перехопив один підписаний колбек, міг би в межах 300 с надіслати ті
самі байти з новим ключем. Коли ключ мусить дорівнювати полям підписаного тіла, повтор із тим самим
ключем — дублікат, з іншим — 400.

**Сховище ключів** — база чи KV з унікальним обмеженням. Пам'ять процесу — лише для демо: на
serverless обробники не ділять стан між запитами.

## Ідемпотентність з обох боків

- Next.js → n8n: той самий `idempotency-key` у кожній спробі; в n8n одразу за Webhook — Remove
  Duplicates за цим ключем.
- n8n → Next.js: HTTP Request з Retry On Fail повторює колбек; Next.js відсікає повтори (крок 6) і
  приймає лише ключ, що збігається з підписаним тілом (крок 7).
- І наші повтори, і Retry On Fail в n8n роблять дублікати неминучими — ідемпотентність обов'язкова.
